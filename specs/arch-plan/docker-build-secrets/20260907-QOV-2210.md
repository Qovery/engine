# Architecture Plan — BuildKit build secrets (QOV-2210)

**Date:** 2026-09-07
**Ticket:** QOV-2210 (supersedes QOV-688)
**Repos touched:** engine only

## Context

Every build environment variable whose name matches an `ARG` declared in the Dockerfile is passed
as `--build-arg`, and the value is recorded in the image configuration. Variables flagged as secret
get the same treatment. BuildKit's `--secret` plus `RUN --mount=type=secret` mounts the value into
one build step without writing it to a layer.

Verified during survey:

- `docker buildx build` is already the only build path (`cmd/docker.rs:901` dispatches to
  `build_with_buildkit`), so `--secret` needs no builder change.
- No `image=` driver-opt is set on `buildx create`, so the builder runs buildx's default BuildKit
  image, which supports secrets.
- The cache is exported with `type=registry,mode=max` (`cmd/docker.rs`), so intermediate layers
  carrying an `ARG` value reach the cache registry as well as the final image. `--secret` closes
  that surface too.
- `compute_image_tag` hashes the environment variable map by key **and value**
  (`utilities.rs`, `environment_variables.hash(&mut hasher)`).
- `local_docker.rs` filters the variable map, recomputes the tag, and only then builds
  `image_to_build` and runs the `does_image_exist_remotely` skip check. Anything added to the map
  upstream is therefore invisible to the tag unless the Dockerfile declares it.
- Log obfuscation already covers secret variables for applications, containers, jobs, Terraform
  services and helms (`environment/task.rs`, `get_secrets`), with agentic workflows handled by
  `agentic_workflow_secrets`. The obfuscation list is built from the request, before any `Build`
  exists.

## Structural decisions

### D1 — Route by Dockerfile declaration, not by `is_secret`

`Build.environment_variables` stays `BTreeMap<String, String>`. No new field, no change to the four
`Build` constructors.

Rationale: `is_secret` is needed for neither routing (the Dockerfile decides which names are
secrets) nor redaction (obfuscation is wired upstream of the build and is not gated on how a value
is consumed). Adding it would be a wide, load-bearing-free change.

Consequence to document: a value mounted as a build secret is only obfuscated in logs if the user
stored it as a secret variable. Eligibility is deliberately not gated on `is_secret` — gating it
would produce a "variable missing" outcome for a variable the user can plainly see.

### D2 — Transport secrets with `src=`, not `env=`

Emit `--secret id=NAME,src=PATH`.

Rationale: `cmd/command.rs` logs `info!("command: {:?}", self.command)`, and Rust's `Command` Debug
prints altered environment variables with their values (std, `sys/process/unix/common.rs`, the
non-alternate branch writes `{key}={value:?}` for every altered var). `env=` would print the secret
into engine logs. `src=` puts only a path in argv.

Constraint: the file lives outside the build context. `local_docker.rs` writes a `.dockerignore`
only for the synthesized-Dockerfile path; git builds use the user's, so the context cannot be
relied on to exclude it.

Lifecycle: mode 0600, removed on success, error, timeout and abort. The build can end through
`CommandKiller` without returning normally.

### D3 — Only a literal `id=` resolves a secret

A `RUN --mount=type=secret` with no literal `id=` fails the build early with a Qovery error asking
for one. BuildKit would fall back to the basename of `target`; Qovery does not.

Rationale: `target=/etc/npmrc` resolving to a variable named `npmrc` is technically faithful and
almost never what the author meant. Rejecting an unwirable mount beats silently matching a derived
name. This makes Qovery stricter than plain `docker build`, which is accepted.

### D4 — An unmatched id is not an error

An `id=` with no matching variable produces no `--secret` flag. BuildKit then decides: a mount
declared `required=true` fails the step, any other mount sees an empty secret.

Rationale: a missing `id=` is a static authoring mistake that can always be caught; an unmatched id
is a configuration state that may be intentional. `required=true` is the user's lever, and is the
thing to document.

### D5 — Secrets key the image tag

Widen the retain in `local_docker.rs` to `dockerfile_args ∪ resolved_secret_ids`, so a rotated
secret yields a new tag and a rebuild. Free, given `compute_image_tag` hashes values.

Accepted cost: values are hashed into the tag with `DefaultHasher` (SipHash, fixed key). Not a
direct disclosure, but a weak oracle for a low-entropy secret.

## Scopes

### Scope 1 — Engine: build secrets

`done_when`: a Dockerfile mounting `id=NAME` builds with the value supplied through `--secret`, the
value is absent from the produced image, and existing `ARG` builds are byte-identical in behaviour.

| Component | Responsibility |
|---|---|
| `build_platform/dockerfile_utils.rs` | New extractor returning the literal `id=` values of `type=secret` mounts, and separately flagging id-less secret mounts so the caller can reject them. |
| `build_platform/local_docker.rs` | Reject id-less secret mounts. Widen the retain to args ∪ resolved ids. Split the retained set into build args and secrets; a name declared both ways goes to both. Materialise secrets to files outside the context and guarantee removal. |
| `cmd/docker.rs` | `build` and `build_with_buildkit` take `secrets: &[(&str, &Path)]` and emit one `--secret id=…,src=…` each. |
| `io_models/agentic_workflow.rs` | Populate `environment_variables` from the workflow's variables instead of an empty map, so a `docker_fragment` mounting a secret resolves. |

Applications, jobs and Terraform services need no `io_models` change: they already populate
`environment_variables`.

Parser constraints — this is where a silent miss is most likely:

- Handle `\` line continuations. Secret mounts are written multi-line far more often than `ARG`s,
  and the existing `extract_dockerfile_args` is line-based (`starts_with("ARG ")`).
- Several `--mount` flags on one `RUN`.
- Arbitrary option order within a mount.
- Do not match `type=cache`, `type=bind`, `type=ssh`, `type=tmpfs`, or comments.

Testable in process: the parser, the routing split, the retain-and-tag behaviour, the id-less
rejection. Requires a local registry, as `test_buildkit_build` already does: that `--secret` reaches
a real build. Not testable in process at all: transport over the Kubernetes buildx driver.

### Scope 2 — Qovery test application (`depends_on`: scope 1)

`done_when`: an application deployed on Qovery builds with a mounted secret, and the secret is
absent from `docker history`, the image configuration, and the `mode=max` cache registry.

Also covers: an `ARG`-based application still builds unchanged, and rotating a secret produces a new
image tag. This is the only place `--secret` over the Kubernetes buildx driver is proven, which is
why it is Definition of Done rather than a nice-to-have.

## Risks

- **`--secret` over the Kubernetes buildx driver is unverified.** Low risk given the default
  BuildKit image, but everything else is wasted if it fails. Prove it first.
- **Pre-existing, out of scope:** `cmd/command.rs` already logs `--build-arg NAME=value` at info
  level. Same class of leak as this ticket, but choosing `src=` means this work does not depend on
  fixing it. Follow-up ticket.
- **Agentic workflows are the widest part of the change** and the only service type needing new
  plumbing. Users reach it only through `docker_fragment`.
- **A rotated secret does not invalidate the step that consumes it.** BuildKit leaves secret
  contents out of its solver cache keys by design, so a cached `RUN --mount=type=secret` is reused
  whatever the secret is — and `required=true` is not evaluated when the step is cached. D5 makes
  the image tag change, which forces a build, but the cache still answers the step.

  Accepted, not worked around. For the dominant use case — a credential used to fetch dependencies
  — reusing the cached layer is the correct outcome: the dependencies were already fetched.
  Forcing `--no-cache` on any build that mounts a secret would make every such build fully cold to
  fix a case that mostly does not need fixing, and `build_disable_buildkit_cache` already gives the
  user that lever per service. Feeding a hash of the values into the cache tag would work only by
  pointing `--cache-from` at an empty ref, which is the same cold build plus a registry ref per
  secret value, with a hash of the secret in the ref name.

  What to document for users: rotating a build secret does not by itself re-run the step that reads
  it. Disable the build cache for that service when it must.
